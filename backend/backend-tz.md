# CTS — ТЗ на бэкенд

Oct 1, 2026 · @Grenen

## 1. Общее

Бэкенд CTS — это **Django REST API + WebSocket-сервер + фоновые задачи**, которые обслуживают все 57 экранов из «ТЗ на фронтенд». Фронт не содержит бизнес-логики: сетку, статусы матчей, права и лимиты тарифов считает только бэкенд.

**Продукт.** CRM для киберспортивных турниров: регистрация команд, автогенерация сетки, расписание и результаты, база участников с историей, уведомления; freemium-подписка для организаторов.

### Стек

| Задача | Технология | Зачем |
| --- | --- | --- |
| Язык и фреймворк | Python 3.10, Django 5.x | Основа проекта, ORM, админка для команды CTS |
| API | Django REST Framework | Сериализаторы, вьюсеты, права, пагинация |

### Принципы

- **Источник истины — бэкенд.** Любое право, лимит и переход статуса проверяется на сервере, даже если фронт уже скрыл кнопку
- Бизнес-логика — в слое сервисов (`services.py`), а не во вьюхах и сериализаторах
- Все даты хранятся и отдаются в **UTC** (ISO 8601); часовой пояс турнира и пользователя — отдельные поля
- Все справочники (игры, форматы, тарифы, шаблоны регламентов) — в базе и редактируются из админки, а не в коде
- Деньги — в минимальных единицах (тыйын) целым числом + код валюты (KGS)

## 2. Архитектура

Бэкенд — один Django-проект (модульный монолит), запущенный в трёх ролях: REST API, WebSocket-сервер и Celery-воркеры. Код общий, разные только точки входа — микросервисы на этом этапе не нужны.

## 4. Роли, права и лимиты тарифов

Доступ проверяется на трёх уровнях: **роль на платформе**, **роль в организации или команде** и **тариф организации**. Все три проверки — DRF-permission классы и сервисные функции, переиспользуемые в API, WebSocket и Celery.

### Роли

| Уровень | Роль | Как получается |
| --- | --- | --- |
| Платформа | Гость | Нет токена |
| Платформа | Пользователь | Зарегистрирован; может быть и игроком, и организатором |
| Платформа | Суперадмин CTS | `is_staff`; доступ к `/api/v1/control/…`, все действия пишутся в AuditLog |
| Команда | Капитан | `Team.captain`; подаёт заявки, вносит счёт, управляет составом |
| Команда | Игрок | `TeamMember`; чек-ин, просмотр |
| Организация | Владелец, Админ, Судья, Модератор | `OrgMember.role` |

### Права сотрудников организации (экран 42)

| Действие | Владелец | Админ | Судья | Модератор |
| --- | --- | --- | --- | --- |
| Создавать и удалять турниры | да | да | нет | нет |
| Одобрять заявки | да | да | нет | да |
| Вносить и менять результаты | да | да | да | нет |
| Решать споры | да | да | да | нет |
| Рассылки | да | да | нет | нет |
| Подписка и оплата | да | нет | нет | нет |
| Управлять командой организаторов | да | нет | нет | нет |

Матрица хранится в коде как одна таблица прав и отдаётся фронту в `GET /me/` в виде списка разрешений по каждой организации — фронт **не дублирует** логику ролей.

### Лимиты тарифов

| Возможность | Free | Pro | Лига |
| --- | --- | --- | --- |
| Активные турниры | 3 | без лимита | без лимита |
| Форматы сетки | SE, DE, Группы | все | все + сезоны |
| Организаторов в команде | 1 | 3 | 10 |
| Брендирование страницы | нет | да | да |
| Уведомления и рассылки в Telegram | нет | да | да |
| Экспорт базы участников | нет | да | да |
| Аналитика | базовая | расширенная | расширенная |
| Взнос за участие | нет | да | да |
| Свой домен | нет | нет | да |
| Рассылок в месяц | уточнить | 1000 | уточнить |

- Лимиты лежат в `Plan.limits` (JSON) и редактируются из админки — **никаких `if plan == 'pro'` в коде**, только `org.has_feature('branding')` и `org.within_limit('active_tournaments')`
- Превышение лимита — ответ `403` с кодом `plan_limit_reached` и названием лимита, фронт показывает модалку апгрейда
- При отмене Pro турниры и история остаются, ограничивается только создание новых

## 5. Аккаунты и авторизация

Вход — по **JWT в httpOnly-cookie**: access живёт 15 минут, refresh — 30 дней (или до закрытия браузера без «Запомнить меня»). Refresh ротируется при каждом обновлении, старый попадает в чёрный список.

### Регистрация и подтверждение (экраны 16, 18–20)

1. `POST /auth/register/` — роль, ник, почта, пароль, согласие с документами (сохраняется версия документа и время согласия). Ник и почта уникальны без учёта регистра
2. Отправляется 6-значный код на почту: живёт 10 минут, не больше 5 попыток ввода, повторная отправка — не чаще раза в 60 секунд. Альтернатива — код по SMS или через Telegram-бота
3. `POST /auth/verify/` подтверждает почту; до подтверждения пользователь не может подавать заявки и создавать турниры
4. Онбординг: `PUT /me/games/` (выбранные игры) и привязка игровых аккаунтов

### Вход, выход, восстановление (экраны 15, 17)

- `POST /auth/login/` — по почте **или** нику; ошибка всегда одна: `invalid_credentials`
- Rate-limit: 5 неудачных попыток за 15 минут на аккаунт и IP → требуется капча или пауза
- `POST /auth/password/forgot/` — всегда отвечает `200`, даже если почты нет (защита от перебора адресов); ссылка с токеном живёт 30 минут и одноразовая
- `POST /auth/password/reset/` — новый пароль; все остальные сессии завершаются
- `POST /auth/logout/`, `POST /auth/refresh/`
- Пароль: минимум 8 символов, буквы, цифры, спецсимвол; хеш — Argon2

### OAuth и привязка аккаунтов

- Вход через **Discord, Google, Telegram** (django-allauth; Telegram — через Login Widget с проверкой подписи)
- Если почта из OAuth совпадает с существующим подтверждённым аккаунтом — аккаунты связываются, иначе создаётся новый
- Игровые аккаунты: Steam — через OpenID, Discord — OAuth, Riot ID — \[уточнить, есть ли доступ к Riot API\]; если API нет — ввод вручную со статусом «не подтверждён», проверка организатором
- Один игровой аккаунт нельзя привязать к двум пользователям

### 2FA и сессии (экран 44)

- 2FA: код через Telegram-бота CTS или TOTP-приложение; 10 резервных кодов, хранятся хешами, показываются один раз
- Код 2FA запрашивается при входе с нового устройства
- `GET /me/sessions/` — список сессий (браузер, ОС, город по IP, последняя активность); `DELETE /me/sessions/{id}/` и «выйти со всех» — отзывают refresh-токены
- Смена почты или телефона — только после кода на **новый** адрес и ввода пароля

### Удаление аккаунта (экран 48)

- Требует пароль и ввод ника; капитан не может удалиться, пока не передал капитанство — ошибка `captain_must_transfer`
- Аккаунт помечается удалённым, через **30 дней** персональные данные анонимизируются задачей Celery; результаты матчей остаются с пометкой «Удалённый игрок»
- `POST /me/export/` — выгрузка всех данных пользователя архивом (JSON), ссылка приходит на почту

## 6. REST API

Все эндпоинты — под `/api/v1/`, JSON, snake\_case. Ниже — минимальный список, который закрывает все экраны; детальные поля описываются в OpenAPI-схеме (`/api/v1/schema/`, Swagger на `/api/v1/docs/` только в dev и stage).

### Соглашения

- **Ошибки** — единый формат: `{"code": "plan_limit_reached", "message": "Лимит активных турниров на Free — 3", "fields": {"email": ["Уже занят"]}}`. `code` — стабильная строка для фронта, `message` — уже переведённый текст
- Статусы: 400 валидация, 401 нет входа, 403 нет прав или лимит, 404, 409 конфликт (например, матч уже изменён), 429 rate-limit, 503 техработы
- **Пагинация** — `?page=&page_size=` (по умолчанию 20, максимум 100), в ответе `count`, `next`, `previous`, `results`
- Фильтры, поиск, сортировка — `?game=valorant&status=open&search=osh&ordering=-starts_at`
- Язык ответа — по `Accept-Language` или настройке пользователя
- Оптимистичная блокировка для матчей, сетки и турниров: поле `version`, при расхождении — `409`
- Каждый ответ содержит заголовок `X-Request-ID`

## 7. Турнирная логика

Это сердце продукта: статусы турнира и матча — **конечные автоматы**, переходы идут только через сервисные функции (`start_tournament()`, `confirm_score()`), прямая запись поля `status` запрещена.

Отменить можно до завершения; после запуска меняются только время матчей и результаты, а игра и формат фиксируются уже при публикации.

### Статусы турнира

| Статус | Что можно | Переход |
| --- | --- | --- |
| `draft` | Менять всё, автосохранение шагов мастера | `publish` — проверка всех полей и лимита активных турниров |
| `registration` | Подача и проверка заявок; игру и формат менять нельзя | Автоматически по `reg_closes_at` или вручную |
| `seeding` | Посев, генерация и перегенерация сетки, расстановка по слотам | `start` — сетка блокируется |
| `live` | Чек-ин, счёт, споры, перенос времени | Автоматически после подтверждения финала |
| `finished` | Только просмотр; начисление очков рейтинга и достижений | — |
| `cancelled` | Только просмотр, уведомление всем участникам | — |

На фронте показываются «человеческие» статусы (Регистрация, Групповой этап, Идёт, Финал, Завершён) — API отдаёт поле `display_status`, вычисленное из статуса и текущего этапа.

### Заявки (экраны 25, 34)

- Подать может только капитан, одна заявка на команду; игрок не может быть в двух заявках одного турнира
- Автопроверка состава при подаче и при каждом изменении: размер (основа + запасные по настройкам игры), привязанные игровые аккаунты, санкции. Результат — в `issues`: `missing_game_account`, `incomplete_roster`, `banned_player`
- Без ручной проверки заявка без проблем одобряется сразу
- Когда места закончились — лист ожидания (если включён), освободившееся место предлагается первой команде в очереди
- `bulk-approve` одобряет только заявки без `issues` и не больше свободных мест
- Для турнира «по приглашениям» заявку может подать только приглашённая команда

### Генерация сетки (экран 35)

- Алгоритмы — в отдельном модуле `brackets` как чистые функции: на вход список команд с посевом и настройки, на выход структура матчей со ссылками `winner_to` / `loser_to`
- **Single Elimination** — стандартный посев (1 против последнего), дополнение до степени двойки «баями» (автопроход верхних посевов), опциональный матч за 3 место
- **Double Elimination** — верхняя и нижняя сетка, гранд-финал; сброс сетки (bracket reset) — настройка
- **Группы + плей-офф** — змейка по группам, круговой турнир в группе, таблица (очки → личная встреча → разница раундов), N лучших из группы идут в плей-офф с перекрёстным посевом
- **Швейцарская система** (бета) — пары по очкам без повторов, следующий раунд создаётся после завершения предыдущего
- Посев: вручную (порядок с фронта), по рейтингу CTS, случайно (seed случайности сохраняется для проверки)
- Коды матчей генерируются предсказуемо: GR-A-01, QF-01, SF-01, GF, UB-R1-01, LB-R2-03
- Перегенерация разрешена до `start`, перезаписывает черновик сетки целиком в транзакции
- API отдаёт сетку в форме, удобной для отрисовки: этапы → раунды → матчи, с подписями пустых слотов («Победитель QF-01»)

### Расписание и чек-ин (экраны 37, 38, 26)

- При постановке матча в слот сервер проверяет конфликты: занятая площадка, команда в двух матчах, буфер между матчами (15 минут), матч раньше матчей, от которых он зависит — ошибка `schedule_conflict` с описанием
- Перенос времени уведомляет капитанов, если включена настройка
- Чек-ин открывается за `checkin_open_min` (60) и закрывается за `checkin_close_min` (10) до матча; команда «готова», когда отметились все основные игроки
- Организатор может продлить чек-ин, снять отметку, напомнить, дисквалифицировать; «Закрыть и построить» заменяет непришедшие команды тех. поражением
- Команда, не прошедшая чек-ин, получает тех. поражение, в базе участников растёт счётчик неявок

### Счёт и споры (экраны 26, 36)

1. Капитан любой команды вносит счёт по картам + обязательный скриншот → матч `awaiting_confirmation`. Валидация: счёт соответствует BO (для BO3 — 2:0 или 2:1), в карте есть победитель
2. Капитан соперника подтверждает → `confirmed`; без ответа 15 минут → автоподтверждение (Celery)
3. Соперник открывает спор → `disputed`, судья и организатор получают уведомление; обе стороны прикладывают доказательства
4. Решение судьи: победа одной из команд с итоговым счётом, переигровка (новый матч в том же слоте сетки) или тех. поражение; решение и комментарий пишутся в AuditLog
5. После `confirmed` победитель автоматически проходит в `winner_to`, проигравший — в `loser_to` (Double Elim), пересчитывается таблица группы, событие уходит в WebSocket

- Исправление уже подтверждённого счёта судьёй возможно, пока следующий матч не начался; иначе — `409 next_match_started`
- Подтверждение гранд-финала завершает турнир: места, достижения, задача пересчёта рейтинга, уведомления участникам

## 8. Real-time и уведомления

Любое событие турнира (новый счёт, перенос, чек-ин) публикуется **один раз** через сервис событий, а дальше расходится в WebSocket и в уведомления по каналам пользователя. Так сокет и Telegram никогда не расходятся по данным.

### WebSocket (Django Channels)

- Одно подключение `wss://…/ws/` на вкладку, авторизация по той же cookie; гость может подписываться только на публичные каналы
- Клиент шлёт `{"action": "subscribe", "channel": "tournament:osh-open"}`, сервер проверяет права на канал
- Сообщения — компактные события, а не целые объекты: `{"type": "match.score_updated", "match_id": …, "score_a": 1, "score_b": 1, "version": 7}`; фронт по ним обновляет кэш или дозапрашивает данные

| Канал | Кто подписан | События |
| --- | --- | --- |
| `tournament:{slug}` | Все на странице турнира | bracket.updated, match.status\_changed, match.score\_updated, schedule.changed |
| `match:{id}` | Страница матча, участники | map.score\_updated, report.submitted, dispute.opened, checkin.updated |
| `user:{id}` | Только сам пользователь | notification.created, counters.updated, invite.received |
| `org:{id}:tournament:{id}` | Сотрудники организации | application.created, checkin.updated, dispute.opened |

### Уведомления

| Событие | Кому | Каналы по умолчанию |
| --- | --- | --- |
| Напоминание о матче (за 60 и 10 минут) | Игроки обеих команд | CTS, Telegram |
| Чек-ин открыт | Игроки команд | CTS, Telegram, push — приходит даже в тихие часы |
| Изменение времени или площадки | Игроки, капитаны | CTS, Telegram, почта |
| Результат внесён / подтверждён / спор / решение судьи | Капитаны, игроки | CTS, Telegram |
| Приглашение в команду, на турнир, на скрим | Получатель | CTS, Telegram, почта |
| Новая заявка на турнир | Организатор, модераторы | CTS, почта |
| Заявка одобрена / отклонена (с причиной) | Капитан | CTS, Telegram, почта |
| Новости CTS | Подписанные | Почта |

- Каждое уведомление создаётся записью `Notification`, затем Celery-задача рассылает по каналам с учётом `NotificationPreference` и тихих часов (сообщения из тихих часов откладываются до их конца)
- Тексты — шаблоны на языке получателя
- Отправка идемпотентна: ключ «событие + получатель + канал», повтор задачи не дублирует сообщение
- Telegram-бот: привязка через deep-link `t.me/cts_bot?start=<token>`, кнопки-ссылки в сообщениях («Открыть матч», «Я на месте»)
- Push — Web Push (VAPID); протухшие подписки удаляются при ответе 410

### Рассылки организатора (экран 40)

- Сегменты: все участники организации, участники турнира, только капитаны, по меткам из базы участников
- Переменные `{капитан}`, `{команда}`, `{турнир}`, `{время_матча}` подставляются для каждого получателя; неизвестная переменная — ошибка валидации
- `POST /mailings/preview/` отдаёт готовый текст для превью
- Отправка батчами через Celery с учётом лимитов Telegram (не больше \~25 сообщений в секунду); статус и % прочтения обновляются
- Отложенная отправка — Celery ETA; отмена до отправки
- Лимит рассылок в месяц — по тарифу, Telegram-канал — только Pro и выше

## 9. Подписки и платежи

Подписка оформляется **на организацию**, а не на пользователя. Платёжный сервис пока не выбран — интеграция делается через абстрактный адаптер `PaymentProvider`, чтобы провайдера можно было заменить без переписывания логики.

### Поток оплаты

1. Владелец выбирает тариф и период → `POST /orgs/{org}/billing/subscribe/` создаёт платёж в статусе `pending` и возвращает ссылку или токен виджета провайдера
2. Пользователь платит **на стороне провайдера** — данные карты к бэкенду CTS не попадают, хранится только токен, бренд, последние 4 цифры и срок
3. Провайдер присылает вебхук → проверка подписи → платёж `succeeded`, подписка `active`, `current_period_end` сдвигается
4. Вебхуки идемпотентны (по id события провайдера), неизвестные события логируются и игнорируются

### Жизненный цикл подписки

- Статусы: `trialing`, `active`, `past_due`, `canceled`, `expired`
- Автопродление: за 1 день до конца периода — списание; при ошибке — `past_due`, повторы через 1, 3 и 5 дней и письма владельцу; после — откат на Free
- Отмена: подписка работает до конца оплаченного периода, затем Free; турниры и история сохраняются
- Смена тарифа вверх — сразу, с перерасчётом остатка; вниз — с начала следующего периода
- Промокоды: скидка в процентах или бесплатные месяцы, ограничение по тарифу, сроку и числу активаций
- Счета: PDF-квитанция на каждый платёж, реквизиты организации (название, ИНН) — в счёте

### Взносы за участие в турнирах (Pro)

- Если у турнира есть взнос, заявка после отправки получает статус `awaiting_payment` и становится `pending` только после оплаты
- Возврат взноса при отклонении заявки или отмене турнира — \[уточнить у заказчика правила и комиссию CTS\]

### Метрики для админки (экран 51)

- MRR, число активных Pro и Лига, отток за месяц, транзакции с фильтрами «Ошибки» и «Возвраты» — считаются запросами к Payment и Subscription, кэшируются на 10 минут

- Публичные картинки — через CDN; приватные (скриншоты, клипы) — подписанные ссылки на 15 минут

### Поиск

- `GET /search/?q=` — турниры, команды, игроки, до 5 результатов каждого типа; PostgreSQL full-text + `pg_trgm` для опечаток в никах
- Поиск в каталоге, базе участников и админке — тот же механизм через django-filter

### Рейтинг (экран 09)

- Очки начисляются за место в завершённом турнире CTS; таблица очков по местам и множитель по размеру турнира хранятся в настройках — \[формулу утвердить с заказчиком\]
- Пересчёт — Celery-задача после `tournament.finished`, результат — снимок `RankingEntry` по сезону, игре и городу; Δ за неделю — разница с прошлым снимком
- Рейтинг игроков считается по результатам команд, в составе которых они играли

### Статистика и аналитика

- Профили (07, 08): турниры, матчи, победы, винрейт, трофеи — денормализованные счётчики, обновляются по событиям, а не считаются на лету
- Статистика игроков в матче (K/D/A, ACS) — вводится организатором или подтягивается из игрового API \[где доступно\]
- Аналитика организатора (41): заявки по неделям, явка, новые игроки, среднее время турнира, популярные игры, **воронка регистрации** (просмотры страницы → начали заявку → подали → одобрены → пришли на чек-ин). Для воронки нужен лёгкий трекинг событий `tournament.viewed` и `application.started`
- Агрегаты кэшируются в Redis на 10–15 минут; тяжёлые отчёты считаются ночью

### Контент

- Статьи хранятся как структурированный JSON (формат редактора Tiptap/ProseMirror), HTML для отдачи санитайзится
- Статусы: черновик → запланировано → опубликовано; публикация по расписанию — Celery
- Правовые документы версионируются; согласие пользователя сохраняется с версией документа
- FAQ и баннеры главной — с порядком и флагом активности

## 11. Нефункциональные требования

### Безопасность

- HTTPS везде, HSTS; cookie `HttpOnly`, `Secure`, `SameSite=Lax`; CSRF-защита для запросов с cookie
- CORS — только домены фронта; для своих доменов организаций (тариф Лига) — динамический список из базы
- Rate-limit (Redis): вход, регистрация, коды, восстановление, контактная форма, поиск, создание приглашений
- Права проверяются на **уровне объекта**: игрок не может внести счёт чужого матча, судья другой организации не видит споры
- Персональные данные (имя, телефон, контакты капитана) видны только организатору турниров, где участвует игрок
- Секреты — только в переменных окружения; в репозитории нет ключей
- Зависимости проверяются в CI (`pip-audit`), Django `check --deploy` без предупреждений
- AuditLog для действий суперадмина, судей (результаты, споры, тех. поражения) и смены прав

### Производительность

- Ответ списков и страниц — до **300 мс** (p95) при 10 000 турниров и 100 000 пользователей
- Никаких N+1: `select_related` / `prefetch_related`, проверка в тестах через `django-assert-num-queries`
- Индексы: slug, ник, статус и даты турниров, `match(tournament, status)`, `notification(user, read_at)`
- Кэш публичных страниц турнира, рейтинга и каталога в Redis с инвалидацией по событиям
- WebSocket выдерживает **2 000 одновременных зрителей** одного финала
- Тяжёлое (рассылки, рейтинг, экспорт, импорт CSV, генерация PDF) — только в Celery, API отвечает сразу с id задачи

### Надёжность и данные

- Генерация сетки, подтверждение счёта и решение спора выполняются в транзакции с `select_for_update` — два судьи не могут одновременно продвинуть один матч
- Ежедневный бэкап PostgreSQL с хранением 14 дней + проверка восстановления раз в месяц
- Миграции только вперёд, без потери данных; опасные миграции — в два шага
- Режим техработ: флаг в настройках → API отвечает `503` с временем окончания (экран 56)

### Тесты и качество

- pytest + factory\_boy; покрытие сервисного слоя (сетка, статусы матчей, права, лимиты, платежи) — **от 85%**
- Юнит-тесты генерации сетки для всех форматов и размеров 2–64 команд, включая нечётное число и «баи»
- Интеграционные тесты API по ключевым сценариям: регистрация → заявка → одобрение → сетка → чек-ин → счёт → спор → финал → рейтинг
- Линтеры: ruff, mypy (строгий для `services`), pre-commit
- CI на каждый PR: линт, тесты, проверка миграций, сборка схемы OpenAPI

### Логи и мониторинг

- Структурные JSON-логи с `request_id`, `user_id`, `org_id`; без паролей, токенов и кодов
- Sentry для API, Channels и Celery; алерты на рост 5xx и очереди Celery
- `/healthz` (живой) и `/readyz` (БД, Redis, Celery доступны)

### Окружения и деплой

- Окружения: local (docker-compose), stage, production; данные stage — синтетические
- Сервисы: web (Gunicorn/Uvicorn для API), asgi (Channels), celery-worker, celery-beat, PostgreSQL, Redis
- Деплой через CI по тегу, миграции — отдельным шагом до переключения трафика
- Сиды для разработки: игры, форматы, тарифы, шаблоны регламентов, демо-турнир «Bishkek Cyber Cup» для лендинга и фронта

## 12. Этапы, приёмка и открытые вопросы

## 13. Сверка с фронтендом

Фронтенд уже готов (репозиторий AmirSaidov/CTS, Next.js 16) и работает на моках, поэтому бэкенд подстраивается под его контракт, а не наоборот. ### 13.2 Расхождения — решить до первого этапа

По каждой строке предложено решение; где написано «под фронт», фронт уже работает так и переделывать его дороже.

| Тема | В ТЗ | Во фронте | Решение |
| --- | --- | --- | --- |
| Пагинация | `count`, `next`, `previous`, `results`; `page_size` 20 | `results`, `count`, `page`, `pages` | Под фронт: добавить в ответ `page` и `pages`, `next`/`previous` можно оставить |
| Формат сообщения WebSocket | `{"type": "match.score_updated", …поля}` | `{"channel", "event", "data"}` + ответ `{"event": "pong"}` на ping | Под фронт: конверт `channel` / `event` / `data` |
| Каналы и события WebSocket | `tournament:{slug}`, `match:{id}`, `user:{id}`, `org:{id}:tournament:{id}`; события `bracket.updated`, `match.score_updated`… | `tournament:{slug}` (`match.updated`, `match.advanced`, `bracket.rebuilt`), `match:{slug}:{code}` (`match.score`, `match.finished`), `checkin:{tournamentId}` (`checkin.updated`, `checkin.extended`, `checkin.closed`), `user` (`notification.created`, `invite.created`, `checkin.opponent`, `match.updated`) | Утвердить один список и записать его в OpenAPI-описание или отдельный файл. | Пути организатора и игрока | `/tournaments/{id}/applications/`, `/matches/{id}/checkin/`, `/matches/{id}/reports/` | `/org/tournaments/{id}/applications/`, `/me/matches/{code}/checkin/`, `/me/matches/{code}/result/`, `/confirm/`, `/dispute/` | Под фронт либо поправить `endpoints.ts` — решает бэкендер, главное зафиксировать в OpenAPI |

Для `cancelled` добавить значение во фронт |

| Палитра | Красная (`#E0202E` на `#0B0707`) | Стальная, как в макете | Бэкенда не касается, но `accent_color` по умолчанию в брендинге должен совпадать с выбранной палитрой |
